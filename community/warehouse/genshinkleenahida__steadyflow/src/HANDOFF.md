# 第一阶段 SteadyFlow 交接

## 来源和规则

业务行为以 `warehouse/workspace/baseline/` 为准；本引擎适配自
`warehouse/submissions/round3/deepseek-v4.1-flash__opus-5.5/`，保留其增量寻路、有效半径、
增量派单和下界剪枝，新增位图证明与移动证明缓存。来源在 meta.json 的 based_on 如实记录。
PARAMS 仅读六项；carryCost 固定 1，useAging 固定 false，输出没有 aged 字段。

## 文件

- `main.cpp`、`common.h`：标准输入输出入口 ReadAll、RunSim、Finish。
- `sim.cpp`：typed 状态、输入预解析、输出缓冲、事件、救援、充电、派单、移动、报表及增量 BFS。
- `monotone.h`：按行四个 64 位字覆盖官方 W<=200 的地图；单调路径存在判断及反向可达证明。

## 缓存和正确性边界

`Slot` 存储 uint16_t 距离，源格必须可走。不可走起点仍可经可走邻格出发，起终点相同仍为零。
validR 内的已存距离精确；超过 validR 的查询回退重填。封路局部修补删点影响，解封进行距离松弛；
远事件只缩小有效半径。只读缓存原始指针或 Slot 引用不可跨下一次 getField 调用持有。
标量查询只铺到查询点所在层，并保留精确半径；需要更远距离时继续重填，不把未展开格当作不可达。
选车时只跳过曼哈顿下界严格大于已合格最优距离的候选，等于最优值仍查询以保留大编号平局规则。

动态字段池和静态字段池各有 256 MiB payload 硬上限，充电桩数量不会增大容量。
缓存池需要回收时仅保护机器人当前目标，不为每个充电桩钉住字段。

位图判断仅在两端可走且存在只向目标前进的路径时返回精确曼哈顿距离。
移动时优先使用已有精确距离场；否则在旧当前位置到目标的矩形内，从目标反向构建证明。
每步仅按上、右、下、左检查曼哈顿减少一的可走邻格，首次正命中达到全局距离下界。
目标改变或当前位置离开矩形时重建；矩形内任何真实 BLOCK/UNBLOCK 都使证明失效，
矩形外事件不影响其中的单调路径。证明为假不代表不可达，必须执行完整 BFS fallback。
缓存新增存储在最大 300 机器人、200 行时约 1.92 MiB。

增量派单只跳过已经失败且没有变好的“旧待派订单×旧空闲机器人”组合。
机器人 IDLE 时位置与电量不变；BLOCK 不降低距离，UNBLOCK 必须让旧组合重新尝试。
新订单、重派订单、取消已派、送达、救援和充电完成均正确标记新组合。
被封 pickup 在无同格候选机器人时立即失败，不能为这些订单先建 b/c 距离场。

## 必须保留的基线行为

- 派单距离相同选编号较大的机器人；订单优先级降序、arrival 升序、数字编号升序。
- 已存在订单取消失败仍增加 cancelled；不存在的订单不增加。
- 救援等待满 100 tick 且位置无人占据后恢复 batteryMax/2。
- 充电达到 90% 即变为 IDLE，同 tick 仍可再次派单或前往充电。
- 先判已到达，再判电量与目标封锁；方向平局为上、右、下、左。
- 机器人按编号顺序移动，后者看到前者移动后的占据；DEAD 不占位。
- 目标被封或无路仅增加累计等待，不增加连续拥堵等待；SIDESTEP 使用原阈值与方向。
- 延迟均值使用 (sum + delivered/2)/delivered，热点仍包含被封非墙格并以行优先打破平局。

## 验证

在仓库根目录使用原有 `python community/check.py community/warehouse/genshinkleenahida__steadyflow`。
Linux 与 Windows 分别编译本平台基线和投稿，不能交叉使用两台环境的 CPU 时间。
速度结论以对应平台的官方摘要为准；逐字节对拍仅归一化 CRLF/LF。
所有源码只用标准库、标准输入和标准输出，没有文件或网络访问、额外进程或多线程。
