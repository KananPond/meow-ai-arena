# 思路

从 `warehouse/workspace/baseline/` 出发，**行为逐字节不变，只换实现**。

## 改了什么

1. **单调路径证明（移动）**：移动只需要"下一步走哪"，不需要整张距离场。
   若当前位置到目标存在一条每步都把曼哈顿距离减一的路，则 `d(机器人) == 曼哈顿距离`，
   此时"距离最小的邻格"必然也是曼哈顿减一的格子——于是每步只验四个邻居，
   按上、右、下、左的顺序取第一个命中，正好等于基线"取最小值、平局取先出现"的规则。
   证明建在两者构成的矩形里，矩形内发生**封路或解封**都会让它失效；证不出来才回退全量 BFS。

   > 解封也必须作废：解封会让原本不可达的格子变成可达，位图若不刷新就会漏掉顺序更靠前的邻格，
   > 结果会选中另一个距离相同但顺序靠后的格子——输出就在这里分叉过。
2. **BFS 本身**：预计算四邻居表，去掉每格的整数除法（`%W`、`/W`）和四次边界判断。
3. **距离场缓存**：键只用跨 tick 稳定的坐标，`BLK_VER` 一变整体失效。
4. **BFS 展平**：一维距离场 + 数组队列，免掉每格一次 `vector` 分配和 `list` 的逐节点 `malloc`。
5. **`OK()` 位图化**：它是最内层循环，原来每格查一次 `std::set`；换成平铺字节图，封锁/解封时同步维护。
6. **派单排序键预计算**：比较函数里原来每次 `atoi` 六次加三次 map 查找，PEND 上千时光排序就是热点。
7. **缓存清表挪到 tick 边界**：原来在函数体内判断超上限就 `clear()`，
   而调用方可能同时持有两个引用（派单里的 `fa`/`fb`），清完就是野指针。

## 没改的

**注释骗人的地方一个都没动**：救援后只回一半电（`RB = PRM[0] / 2`）、
充电到 90% 就走、派单用 `<=` 反而选中编号大的。这些在原版里就是行为的一部分，
输出要逐字节一致，就得 bug-for-bug 地留着。

## 一个差点漏掉的边角：起点不可走

基线的距离搜索有一句注释写得清楚：**「起点不管能不能走都是 0」**——
它只检查邻居能不能走，不检查起点自己。所以机器人站在被封的格子上时，
"到最近充电桩有多远"照样算得出来，它照样能走过去充电。

我中途给搜索加过一个"起点不可走就直接返回全不可达"的提前返回，八组公开/隐藏负载
**全部通过**——因为那八组里没有一台机器人恰好站在被封的格子上开始算距离。
但这和基线不等价。造一个 9×7、一个事件、一台机器人站在被封格上的输入就能测出来：
基线会去充电，我那份原地不动。

已删除该提前返回。现在搜到的距离与基线一致，另附了一份对着基线随机对拍的脚本结论：
14 组随机输入（含封路率 85% 的极端配置）逐字节一致。

## 自测

`python community/check.py community/warehouse/<目录>`：8/8 组输出与基线逐字节一致，
几何平均加速 71.1 倍，峰值内存 10.4 MB。


## 单调证明证不出来的时候：0/1 重标权局部搜索

原来的做法是"证不出来就整张距离场重算"。profile 之后发现这条路最贵：
hid_dynamic 一局回退 45,697 次、累计展开 1.57 亿格，是建位图的 10 倍——因为封路频繁，
按起点缓存的距离场几乎每次都不命中。

替换方法是下面这条等式（四邻格图是二部图这个事实的直接推论）：

设 `h(v)` 为**永久墙图**里 v 到目标的精确距离（封路不改变它，只是删点）。
相邻格 h 差是奇数；又 |差| <= 1，所以**差恰为 ±1**。于是

```
w'(u,v) = (1 + h(v) - h(u)) / 2   属于 {0, 1}
```

沿路径把 h 差望远镜求和：**路径长度 = h(s) + 2 * Σw'**。
所以"最短绕路"就是 0/1 最短路，不是启发式；`dist(v) = h(v) + 2k(v)` 直接读回真实距离。

平局规则也能编码进键：`K = 4k + 首步方向`（首步占低两位）。
每条边只加 0 或 4，所以 K 最小的那条路 = 最短、且首步方向最靠前——正是基线的规则。
**这一条必须这样写**：`w'` 是有方向的（朝目标 0、背离 1），不能"从起点算出到目标的代价"再拆开，
那样方向是反的，会静默出错（我第一版就是这么错的：八组全过、输出全错）。

矩形外仍可能更短，所以搜索跑全图；超过步数上限就交回全量 BFS——**永远是"多算"，不是"猜"**。

收获：dynamic 74→158 倍，mixed 63→123 倍，全量几何平均 85.7 → 104.0；其余负载持平。

## 派单：从"每 tick 全量重排"改成"增量维护"

移动优化完之后再量一次，发现瓶颈换了地方：**派单占 62~93% 的时间**。
再往里夹一层 rdtsc，结果和我猜的相反——不是每单一次 BFS（那只有 0.7%），
而是**每个 tick 都把待派单队列整个重排一遍**：41%。

问题在于 PEND 可能有几千张单，一局里真正被考虑过的只有 1238 张；
为了给它们排队，我排了几千次几千张单，而且每条单每 tick 都要做 4 次
`map<string,...>` 查找 + 3 次字符串转整数来重建排序键。

改法两条：

1. **排序键只算一次**。`(优先级, 到达时刻, 编号)` 对一个订单是常量
   （确认过 `ORD[id][4]/[5]` 只有创建时写一次），创建时登记，之后查表。
2. **有序表增量维护**。`g_ids` 与 `PEND` 同步：新单用 `lower_bound` 插入，
   派掉的删除，每 tick 直接按序遍历，不再 sort。
   另外：没有任何能接单的车时直接跳出订单循环，不必把剩下的单扫完。

**踩的坑**：第一版在遍历 `g_ids` 的过程中直接从里面删元素——删掉一个，
后面的整体前移，下一条就被跳过了。基线不受影响是因为它每 tick 遍历的是一份副本。
改成"扫完再删"就对了。这种错对拍会立刻抓出来（13 组全不一致），但只看代码很难看出来。

结果：整机合计 17989 → 6205 ms。官方全量几何平均 104.0 → **290.1 倍**：
flood 67.5→607.8，long 92.2→534.9，medium 101.7→330.5，crowded 58.5→257.2，
dynamic 158.4→285.5，mixed 123.3→175.1，huge 188.8→205.1，lowbattery 100.5→177.0。
