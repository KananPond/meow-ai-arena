# 坦克大战 · 比赛条件与异常记录

> 和其他各集一样，本页公开计入成绩的场次里所有的中断、补时、主办方介入和事故。视频正片为了观感省略了这些细节，以本页为准。时间是比赛电脑的本机时间（美国太平洋时间，UTC−7）。

## 赛制

- 14 个模型，每位上下半场各做一次。本机选手都在同一台 Windows 11 电脑（Intel Core i9-13900HX）上做题，分几批开赛；SolUF、Gemini、Muse 三位由外部操作员在另一台电脑（AMD Ryzen 7 9800X3D）上做。
- 每位选手一个空文件夹，里面只有 `workspace.zip`（即本目录的 `workspace/`，当时基准只给编译好的程序）。开赛提示词所有人逐字相同，见 `prompt.md`。主办方之后只发中场消息、续跑消息和赛后复盘，不追加别的话。
- **计时**：上半场从选手解压 `workspace.zip` 的时刻算起，下半场从解压中场包的时刻算起，选手随时可以用 `clock.py` 看。每个半场 30 分钟，最早第 20 分钟可以交卷（只是规则和提醒，不拦截），到 45 分钟由主办方的计时脚本强制封存当时的 `submission/bot.cpp`。选手提前交卷时主办方手动收卷，一分钟后再核对一次文件有没有变。
- **外部选手**：主办方不能给外部机器计时，也不能强制封存。三位的用时是操作员的记录，bot 由主办方"登记"收下。
- **边界**：禁止联网、禁止求助其他模型（包括子代理）、只能结束自己启动的进程，这些写在提示词里，没有在工具层面禁用。
- **思考档**：没有统一设置，用各工具的默认值。实际记录到的档位：GPT 三位和 Claude 两位是 medium，DeepSeek、Kimi 是 high，Muse 是 high（工具默认），GLM 是 max，Gemini、Doubao、MiMo 是工具的 `variant: default`（不能对应到具体档位），Grok 没有具体值，Qwen 没有设置（工具默认）。
- **评测**：中场赛、终场赛、进步赛都在比赛电脑上用 `tournament/tournament.py` 跑，性能模式，只用大核，每局两个 bot 各占一个物理核，同时 4 局。编译命令 `g++ -std=c++20 -O2 -static`（GCC 16.2.0）。每批（一张图上的全部对局）前后各测一次速，前后相差或偏离基准超过 15% 的批次标记出来，结果照常计入。

## 主办方的失误

- **GLM 被误收卷**（10-14 上半场）：ZCode 出了一次工具故障，主办方把它当成选手交卷，在 05:47:33 收卷封存；05:49:54 发现后作废这份封存，选手续跑，最后 06:04:13 手动收卷。这段停顿另外补了时（见下表 T11）。
- **补时写入晚了约 3 分钟**（10-15 下半场）：Opus、Astra、Sol、Haiku 四位在 04:23–04:29 同时断网，恢复后补时在 04:32:29–04:32:56 才写进计时起点。这几分钟里选手读到的时钟不含补时，比实际多（例如 Haiku 在 04:29:46 读到"已用 10.2 分钟"，补时后同一时刻约 3.6 分钟）。这四次恢复时用户发的是"继续"，不是标准续跑消息。
- **补时有估算成分**：Kimi 上半场的 582 秒，停顿起点是按它最后一次改 bot 的时间估的；10-15 四位的 372/403/407/395 秒比会话记录里可见的空档略大。方向都对选手有利。
- **DeepSeek 封存后工作区又被改**（10-13 上半场）：45 分钟到点强制封存后，dsh 被一条后台任务通知唤醒，自动开了新一轮，把另一份候选代码复制到了 `submission/bot.cpp`。主办方封存后只核对过一次，当时没有发现。成绩以封存副本为准（sha256 前 12 位 `f71626be2ee0`，和 `bots/half1/deepseek-v4.1-flash.cpp` 相同），封存后的改动不算数。
- **Opus 早交卷靠手工补记**（10-15 下半场）：Opus 在第 18.9 分钟结束（按补时后的起点），主办方在第 25.4 分钟收卷，脚本按收卷时刻判断，没有自动标记"早于最早交卷时间"，04:53:11 手工补记。

## 环境带进会话的额外内容

这些都和做题无关，但属于选手没有被告知的额外上下文，影响无法量化。

- **用户的全局个人规则文件**：比赛电脑上有一份用户的全局规则文件，内容是一条和编程比赛无关的个人工作约定。Claude 选手（Opus、Haiku）比赛期间，主办方把它临时改名，赛后改回。10-14 Grok 重跑上半场时没有挪开，Grok Build 把它当作用户规则带进了会话；下半场开始前又挪开了，但 Grok 的下半场是上半场同一个会话的续跑，上下文里仍然带着这段规则。
- **Claude Code**（Opus、Haiku）会把用户安装的技能清单注入会话开头。
- **Codex**（SolUF，推断 Astra、Sol 相同）会话自带基础指令、记忆说明、技能目录、权限和协作规则。
- **Muse**：工具自带预置规则、记忆机制和内部提醒；下半场续跑原会话，带着上半场的历史。
- **`arena.py check`** 的输出会打印比赛电脑上编译器的绝对路径，里面有出题人的用户目录名。对做题没有影响；仓库里的文件不含这个路径。

## 赛后检查

- 28 份封存代码（14 位 × 2 个半场）都只用 `tank.hpp` 和 C++ 标准库，没有读写文件、读环境变量、调用系统命令、开线程或包含 `<windows.h>`。
- `bots/` 里每份代码的 sha256 都和三场比赛清单（`results/*/清单.json`）里记录的一致；基准源码、出题方参照源码、起步模板也一致。
- 用 `tournament/` 里的配置重建赛程，三场比赛的赛程指纹（`games_sha`）都和原赛程相同。开源前在同一台电脑上重打了终场赛的前 352 局：338 局逐回合相同，347 局胜负相同；不同的局都涉及按剩余时间停止搜索的 bot。

## 解读时请注意

- 每个模型每个半场只跑了一次。这是"这一场"的结果，不是严格的 benchmark。
- 工具、渠道、思考档、机器各家不同：五家经 Cline 通行证，不是各家官方接口；三位在更快的外部机器上做题，没有主办方计时；思考档从 medium 到 max 不等。
- 有五位的上半场是重跑的，重跑时它们已经见过这道题。
- 补时是主办方按记录做的判断，部分秒数是估算。Doubao 下半场在第 27.8 分钟因额度用完中止，损失的时间没有补。
- 测速被标记的批次照常计入。相邻名次差的区间含 0 时记为并列，名次之间的差别不要读成确定的强弱。
- 成绩由 `tournament/` 里的程序按事先定好的规则计算，逐局结果都在仓库里，可以复算。
- 原始会话记录、作废场次的数据没有放进仓库，上面关于会话内容的描述来自主办方的记录，读者无法独立核对。
