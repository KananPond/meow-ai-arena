# 仓储调度仿真 · 交接文档

## 1. 结构

| 文件 | 作用 |
|---|---|
| `grid.h` / `grid.cpp` | 地图、封锁状态、可通行判断、BFS 距离表（带缓存）、充电桩列表。 |
| `sim.h` | `Robot`、`Order` 结构体，`Sim` 类声明。 |
| `sim.cpp` | 读入、每个 tick 的各阶段、收尾统计输出。 |
| `main.cpp` | 入口：`Sim(std::cin).run()` 写到标准输出。 |

每个 tick 的阶段顺序（与基线一致，不能调换）：

1. `applyEvents`：按输入顺序处理本 tick 的 ORDER / CANCEL / BLOCK / UNBLOCK。
2. `rescue`：DEAD 满 100 tick 且格子空闲 → IDLE，电量恢复为一半。
3. `chargeRobots`：CHARGING 充电，达到 90% 离开。
4. `dispatch`：派单。
5. `sendLowBatteryToCharger`：低电量空闲机器人去充电桩。
6. `moveRobots`：所有在途机器人按下标顺序移动、到达、停机。
7. `report`：每 `reportEvery` tick 输出一行 REPORT。

最后 `run()` 输出 SUMMARY / LATENCY / ROBOT 行。

## 2. 必须保留的基线行为（看起来像 bug，但都是标准答案）

以下每一条都由对拍确认过。改动前请先看基线，并跑对拍。

1. **派单平局取编号最大的机器人**：`dispatch` 里是 `if (a <= best)`，遍历顺序是下标升序，所以同距离时后遍历到的覆盖前者。SPEC 写的是"取编号小的"，以代码为准。
2. **救援只恢复一半电量**：`batteryMax_ / 2`。SPEC 写的是充满。
3. **充电到 90% 即离开**：`battery * 10 >= batteryMax_ * 9`。
4. **CANCEL 计数包含失败的取消**：`cancelled_++` 放在"订单存在"之后、状态判断之前。已取货、已完成、已取消的订单再次取消，也会计入 `cancelled=`。
5. **平均延迟四舍五入**：`(sum + delivered/2) / delivered`。
6. **充电桩选择分两步**：第一步排除被占用的（有其他机器人在充电或正前往该桩）且电量不够（距离 + 安全余量 > 电量）的；若没有结果，第二步不看占用，选最近可达的桩排队。平局都取行优先靠前的。占用计数只在本阶段内维护，阶段末撤销。
7. **让路不看距离**：连续等待 ≥ 4 次、且下一步不是目标格时，按方向顺序（上右下左）取第一个可通行且空闲的相邻格。让路后仍然会检查是否到达目标。
8. **目标被封锁时只计等待，不计连续等待**，也不会改变状态。
9. **停机判定在移动阶段**：先看是否已在目标格（已在目标格则直接到达，即使电量为 0），再看电量是否为 0 → 停机。
10. **BFS 距离**：起点不论能否通行都作为起点，之后只经过可通行格。`dist(a, b)` 在 a==b 时为 0，b 不可通行时为不可达。a 不可通行时 `dist(a,b)` 与 `dist(b,a)` 可能不同。机器人可以站在被封锁的格子上。
11. **移动时距离表以目标为起点**：选"从目标出发的 BFS 距离最小"的相邻格，平局按方向顺序。
12. **REJECT 条件**：取货点或送货点在图外或是墙。被拒的订单不进入 ORD，之后的 CANCEL 得到 CANCEL_FAIL。
13. **BLOCK 在墙上或图外无效**；UNBLOCK 对未封锁的格无效。
14. **ASSIGN 输出的是 a（机器人到取货点的距离）**。
15. **取消已分配订单**：机器人立即变为 IDLE，电量不变，连续等待清零。
16. **停机**：TO_PICKUP 的订单退回 PENDING，保留原到达 tick，并入待派单；DELIVERING 的订单变为 LOST。
17. **热点**：只统计非墙格；统计的是非停机机器人，包括被封锁的格；取最大值，相同取行优先靠前的格；没有非墙格时输出 `-1,-1,-1`。
18. **报表在移动之后输出**，`pending` 是 PENDING 订单数。

## 3. 优化思路（为什么快）

基线的主要开销：

- 事件循环每 tick 扫描全部事件：O(T × E)。现在改为按 tick 分桶，保持输入顺序。
- 每次距离查询都做一次全图 BFS，派单对每个订单、每个机器人都要做 2 到 3 次 BFS。
- 移动时每个机器人每 tick 都做一次 BFS。
- `OCC` 线性扫描所有机器人：O(NR²) / tick。现在用每格计数 `occ_`。
- 热点统计 O(W·H·NR) / 报表。现在用旋转坐标（u = x+y，v = x−y+H−1）把曼哈顿菱形变成正方形，再用二维前缀和，每格 O(1)。
- 订单用字符串 map 存取、排序时反复解析整数。现在用结构体和预解析的 `idNum`。

具体做法：

- **距离表缓存**（`Grid::distFrom`）：以起点格为键，缓存 uint16 距离表（INF = 65535）。缓存上限 2048 张，每 tick 开头超限则清空。封锁状态一变就整体清空。距离表指针只在两次清空之间有效，所以清空只能在 tick 开头或事件阶段（没有持有指针）时进行。
- **派单代价按订单缓存**（`Order::b`、`Order::c`）：b、c 只依赖地图和封锁，用 `Grid::version()` 判断是否过期。计算 b、c 时用不缓存的 `distUntil()`，避免撑爆缓存。
- **派单候选**：每 tick 先收集空闲且电量够的机器人（下标升序）。派出去一个就从候选里删掉。
- **占据计数** `occ_`：只在机器人移动、停机、救援时更新。`occupied(x, y, except)` 对 except 自己做修正。
- **充电占用计数** `chargeUse_`：阶段开始时计入，阶段末撤销。

派单代价 b、c 用"遇到目标即停"的 BFS（`Grid::distUntil`）计算。BFS 按距离非递减发现格子，所以首次命中的距离就是最短距离，结果与全图 BFS 相同。

公开负载上（`tools/bench.py`，CPU 合计）：基线约 107 秒，当前约 1.1 秒。单项加速比见 bench 输出，`pub_dynamic`（封锁频繁）相对最慢。

**已知性能风险（未解决，下一步优先看这里）**：

- 派单每 tick 对每个待派订单都要扫描候选机器人。待派订单积压很多时（洪峰负载、机器人不够用），这是 O(P × 候选数) / tick。
- 封锁每变化一次，所有订单的 b、c 代价缓存都失效，下一次派单要重新算。封锁频繁且积压很多时，这部分代价最高。
- 实测：200×200、300 机器人、T=20000、约 12000 个订单、约 7900 次封锁变化的输入（`gen.py` 参数：rate=0.6、block=0.2），新程序 CPU 时间超过 2 分钟，仍未跑完。这个输入远超公开负载的规模，基线在它上面更慢（事件循环本身是 O(T×E)），但这个数字说明积压场景还有大量优化空间。
- 可能的改进方向：(1) 待派订单按取货点分组，同一取货点只算一次；(2) 封锁变化时只使受影响的距离表失效，而不是全部清空；(3) 候选机器人为空时直接跳过（已做）之外，对"本 tick 没有变化的订单"做增量判断。改之前请先用对拍确认输出不变。

## 4. 风险与边界

- **距离表用 uint16**：正式规模 200×200 时，最长 BFS 路径远小于 65535（最坏约 40000）。若把地图上限放大到超过约 65000 个可通行格，这里会溢出，需要改成 int32。
- **缓存内存**：2048 张 × W·H·2 字节。200×200 时约 160MB，低于 1GB 上限。
- **热点计算**：每个报表 O(N²)，N = W+H−1。`reportEvery = 1` 且 T 很大时这是主要开销之一。
- **派单 O(P × 候选数)**：待派订单很多（洪峰负载）时这里会变慢，但仍远快于基线。
- **封锁频繁**：每次实际变化都会清空距离缓存，并让所有订单的 b、c 失效。
- **事件坐标**：合法输入里事件坐标可以在 [-1000, 1000]，由 `validPoint` 与 `setBlocked` 的图内检查处理。
- 对拍覆盖：公开负载 5 组，以及随机参数（不同地图尺寸、电量、封锁率、取消率、报表间隔、热点半径）的 `gen.py` 输出，全部与基线逐字节一致（见 `work/fuzz.py`）。

## 5. 想改某类逻辑，去哪里

| 想改的内容 | 位置 |
|---|---|
| 派单规则、优先级排序、候选条件 | `Sim::dispatch` |
| 派单代价 b、c 的计算 | `Sim::routeCost` |
| 充电桩选择、充电占用 | `Sim::sendLowBatteryToCharger` |
| 充电速度、充满阈值 | `Sim::chargeRobots` |
| 救援条件与电量 | `Sim::rescue` |
| 移动、让路、等待、停机 | `Sim::moveRobots`、`Sim::die` |
| 到达后的状态转换 | `Sim::arrive` |
| 订单取消、拒绝条件 | `Sim::onCancel`、`Sim::onOrder` |
| 报表与热点 | `Sim::report` |
| 收尾统计（平均延迟等） | `Sim::run` |
| 距离语义、缓存策略 | `grid.cpp` |

注意：改派单或移动逻辑时，要同时确认 `occ_`、`chargeUse_`、`pending_` 与机器人、订单状态保持一致。`pending_` 只包含 PENDING 订单（集合语义，排序后使用）。

## 6. 怪行为清单（改之前请先确认）

- 取消 ASSIGNED 订单时，机器人直接回到 IDLE，不做任何收尾。
- DEAD 机器人的目标格被清空，但救援后 `waitStreak` 清零、`deadTick` 置为 −1。
- CHARGED 后机器人保持原来的 `waitStreak`，但下一次进入 TO_* 状态时会被重新清零，所以没有实际影响。
- 同一 tick 内，机器人到达取货点后会立即转为 DELIVERING 并以送货点为目标，但本 tick 不再移动。
- 移动阶段的让路可以让机器人走到目标格上，此时同样会触发到达处理。
